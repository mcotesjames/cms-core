> [!IMPORTANT]
> This is the MCJames Visual CMS platform repo. It began as a copy of an earlier client build and is
> fully cut off from it: no `.env`, no Supabase project, no Lovable project, no live deploy target. Never
> reconnect it to that build's repo, database, Lovable project or Worker, and never name that client
> in code, content or docs. Why: nothing done here may affect the original client's live site.
>
> Never rewrite pushed history (force pushing, or rebasing/amending/squashing pushed commits).

- `cms-platform-spec.md` is the single source of truth for the CMS platform. After any change to the CMS or Studio, update the affected sections and add a dated entry to its change log (section 17); add reusable learnings to section 16. Why: the platform is reused for every site, so the spec must always match what's built.
- Data lives in Cloudflare D1 (`DB`) and R2 (`MEDIA`), declared in `wrangler.jsonc`. Locally, `npm run db:reset` builds the local database from `migrations/platform/` and seeds `db/seed.sql` (fixtures only, never client data); `npm run dev` then uses it through Wrangler's platform proxy (`src/data/env.server.ts`). Schema changes: edit `src/data/schema.ts`, run `npm run db:generate`, commit the new SQL file; never edit an applied migration. Why: each site has its own database and bucket, and migrations are the only way the schema changes.
- `src/data/` is the only code that touches D1 or R2. Routes and components call its server functions; every `createServerFn` lives there and starts its chain with exactly one access middleware from `src/data/access.ts`: `asVisitor` (public reads of live columns only, never `draft`) or `asEditor` / `asAdmin` / `asCollaborator` (Studio, receives `context.user`). `src/test/server-fns.test.ts` fails otherwise. Import server-only modules (`db.server`, `schema`, `env.server`, `session.server`) inside handlers with `await import(…)`. Return types must be serializable: use `Json` / `JsonObject` from `src/data/shapes.ts`, never `unknown`. Why: access is denied by default and enforced in one place.
- Public responses go through the edge cache (`src/data/cache.server.ts`, wired in `src/server.ts`): pages are keyed by path + build id (`__BUILD_ID__` from `vite.config.ts`, so a deploy never serves HTML pointing at the previous build's removed assets) + content version (`site_content.updated_at`), so `updated_at` must change only when live content changes (Publish, Settings saves) and never on draft saves; media is keyed by address. Never cache `/admin`, `/_serverFn` or `?studio=1`, and keep browser caching of pages at `max-age=0, must-revalidate`. Why: the Cache API is per data centre, so purging can't clear every copy; a version key refreshes them all within seconds.
- Environments: `wrangler.jsonc` is the staging Worker (`cms-core-staging`, D1 `cms-core-staging`, R2 `cms-core-staging-media`, `SITE_ENV=staging`), deployed at https://cms-core-staging.mcotesjames.workers.dev by GitHub Actions (`.github/workflows/ci.yml`: every push to `main` that passes the checks applies staging migrations, then deploys the built Worker; never deploy staging from a laptop except as a fallback with `npx vite build && npx wrangler deploy --config .output/server/wrangler.json`); remote database commands take `--remote` (migrations: `npx wrangler d1 migrations apply DB --remote`). Local development uses its own database via `preview_database_id: "local-dev"`, never staging's. Anything but `SITE_ENV=production` is noindexed (robots.txt and `X-Robots-Tag`). Why: staging can be shown to clients without being indexed, and local experiments never touch deployed data.
- `vite.config.ts` is a plain TanStack Start config: Nitro (`cloudflare-module` preset) runs only for builds, writing the Worker and its `wrangler.json` (from `wrangler.jsonc`) to `.output/`. Test a build with `npx wrangler dev --config .output/server/wrangler.json --persist-to .wrangler/state`. Why: `vite dev` doesn't exercise the Worker runtime or the edge cache.
- The schema keeps the spec's generic tables (`entries`, `records`, `list_items`) for content types, record types and section items, but the skeleton site uses none of them yet: everything a visitor sees comes from `site_content`. Why: content types and records come back as platform features without a migration.

- Site content (pages, menus, settings) lives in D1 and is edited at /admin; never hardcode it in components. Why: the client edits content without code changes.
- Sign-in is Better Auth with email + password (`src/data/auth.server.ts`, `/api/auth/*`), built per request from the request's origin; `currentUser()` joins the session to the `users` row. Studio access is that row's `role`: `pending` waits for approval in Settings → Users (`/admin/users`, admin-only); admins approve as editor or admin, change roles, remove access (deleting the person's sessions) and set temporary passwords; the `collaborator` (MCJames: the first sign-up matching the site's `COLLABORATOR_EMAIL` while it has none is approved as collaborator automatically; `npm run user:collaborator -- <email> [--remote]` hands the role over) and your own account can't be changed. Sign-up never sets a role. Never seed accounts or passwords onto a deployed site: `db/seed.sql` is content only, and the password-less shortcut accounts in `db/seed.dev-users.sql` (cookie `cms_dev_user`) exist only in `vite dev`. `BETTER_AUTH_SECRET` and `COLLABORATOR_EMAIL` are Worker secrets per environment (`.dev.vars` locally), never printed or committed. Keep a single zod (v4): Better Auth breaks in the production bundle on zod 3. Why: deployed Studios are public, so access must come only from real accounts an admin approved.
- Uploaded media goes through `uploadMedia` (`lib/media.ts`): images are resized in the browser (max 2400px, quality 0.82; SVG/GIF/other files unchanged), stored in R2 under `library/<timestamp>-<name>` with a `media` row, and referenced by the stable path `/media/<key>` (served by `routes/media.$.ts` with a one-year immutable cache). Never store expiring links. Share images go through `absoluteUrl` in `lib/seo.ts`. Why: stable addresses never break, and Workers can't resize images.
- The public site is a plain, neutral skeleton (white, near-black text) meant to be restyled per site: its styles are the `.site-*` rules in `src/site/theme.css`, driven by the tokens in `:root` (colours, `--page-gutter`, `--measure`, `--wide`, `--type-h1`, `--type-h2`, `--type-lead`). No motion libraries, WebGL or page transitions. Header: site name left, main menu right, a Menu toggle below 768px. Why: a neutral base every site starts from, with nothing to strip out.
- Satoshi (300, 400, 500, 700) is the public site's only web font (the Studio uses self-hosted Inter, which visitors never download): loaded from Fontshare's CDN in the root head and used by `--font-sans` / `--font-display`, numerals included (tabular figures). Text weight is `--weight-text` and the public H1 weight `--weight-h1`, both in `src/styles.css` (a site overrides them in `src/site/theme.css`); never hard-code font weights. Why: one typeface, with its weight set in one place.
- Page text and site settings live in the site_content table (one row per page plus `settings`, `menus` and `pages`, each with live content plus a nullable draft), loaded once in the root loader. Why: one home per page with room for the draft/live flow.
- Content Studio edits go to the nullable `draft` column of site_content; Publish copies the draft to the live content and clears it (`publishSiteRow`), public pages read only live content. Drafts are read only through Studio server functions (`lib/admin-drafts.ts` wraps them); `asVisitor` functions never select `draft`. Why: edits never reach the site until published, and drafts stay admin-only.
- Full-screen editors are `admin_` routes outside the /admin layout and share StudioShell: the real page in an iframe (`?studio=1`) where StudioBridge edits `data-cms` text in place and shows hover ↑/↓/+ on `data-cms-section` blocks; the side panel only edits the selected block's fields. `/admin` redirects to Pages (the site has no content type yet). Sidebar groups: Feedback, Pages, Library (Media), Settings (Site settings, Users). The editor title is the page switcher (`components/admin/PageSwitcher.tsx`, `lib/page-switcher.ts`): pages with orange (unpublished) / purple (unresolved comments) dots, search, Cmd/Ctrl+K (forwarded from the canvas as `studio-shortcut`); it waits for pending saves and carries `device` / `mode=comment` in the search params. Editors are keyed by what they edit (`PageCanvas key={key}`). Why: one editor behaviour everywhere, matching the live site, and quick moves between editors without state leaking between them.
- The Content Studio uses its own "Panelled" theme (spec section 4 → Studio theme): AdminGate wraps every admin screen in `.studio`, and `:root:has(.studio)` in styles.css defines the `--st-*` tokens (canvas, card, line, text greys, primary, accent, status colours, shadows, durations) and maps the shared tokens onto them (primary = near-black, ring = blue accent, accent = hover fill). Each screen's content sits in the layout's white `.studio-card`; lists use `.studio-rows` / `.studio-row`; status is Badge `live` / `changes` / `draft` (dot + word, never colour alone); one filled primary button per screen; Lucide icons at 16px, stroke 1.75. Studio text is Inter (self-hosted `@fontsource-variable/inter`), 14px base, weights 400/500/600. Never restyle admin screens with page-level backgrounds or hardcoded colours; use the `--st-*` tokens. Why: one calm, consistent admin across every site, separate from each site's look.
- Every page is a pinned hero plus flexible sections, rendered by `PageView` (`components/sections/PageSections.tsx`) for both the homepage (`routes/index.tsx`) and created pages (`routes/$slug.tsx`). The hero is the page row's `intro.title` (the page's one H1) and `intro.summary`; `lib/page-sections.ts` defines the section library (Text: heading + body; Image: image, alt, caption, contained / full width), and a page row stores `sections` (order) and `section_data` (each section's own fields). Add new section types to the library rather than hardcoding them into a page. Why: every page is built and edited the same way.
- Studio canvas outlines: blue (`--studio-section`) for `[data-cms-section]`, cyan-blue (`--studio-inner`) for `[data-cms]`, `[data-cms-image]` and `[data-cms-item]`; dashed on hover, solid when selected. Item outlines sit outside the element unless it carries `data-cms-fill` (fills its section), which insets them. Selection flashes are fixed overlays added by StudioBridge. Why: a negative outline offset collapses on small items, and overlays never affect layout.
- Menus are edited on the Studio canvas, not hardcoded: `lib/menus.ts` defines links (which point at a page, a page section, a URL or an email, never a raw path), the footer column limit (3) and the defaults (Home in the main menu, a Contact column in the footer); SiteChrome renders them from the site_content row `menus` (draft/live) and hides links whose target has gone. Page sections get an anchor `section-<id>` (`sectionAnchor`) for section links. Edited in the page editor via `components/admin/MenuPanel.tsx` (`data-cms-section="menus:main"`/`"menus:footer"`, links `data-cms-item="menu:<id>"`, columns `"menucol:<id>"`). Why: the client edits navigation visually without code changes, and links survive renames and reordering.
- Empty CMS content is never rendered on the live site: wrap every CMS-fed element, its containers and its section in `useShow()` from `lib/show-if.ts` (`{show(a, b) && …}`; `isFilled` for values that are never edited in place). In the Studio canvas `useShow` always renders, and empty `[data-cms]` text gets an "Empty — hidden on the site" placeholder from styles.css; an empty image shows an upload placeholder. Why: no empty tags, gaps or broken images when the client leaves a field blank, while the field stays fillable in the editor.
- Feedback comments (`comments` table): `lib/comments.ts` (threads, which threads show on a canvas, places), `components/admin/useComments.ts` (data + actions), `CommentThreads.tsx` (new thread, thread view, rows), `useCanvasComments.tsx` (comment mode in StudioShell editors). Threads are pinned to the canvas's own element addresses (`data-cms`, `data-cms-image`, `data-cms-item`, `data-cms-section`) and remember where they were left (`opened_on` = `page:<key>`); menu and footer threads show on every page. StudioBridge only draws pins while comment mode is on, and pauses editing then; a click also stores `comments.position` (path from the anchored element to the clicked element + click point as fractions, see `parsePosition`) so the pin lands on that exact spot, drawn hollow on the nearest visible part when it's inside something closed. Alt/Option-click passes through to the page while commenting. Keep interactive open/closed state in attributes (`data-open`, `aria-hidden`, `aria-expanded`) so pins can tell when content is hidden. Why: comments survive edits and reordering with no extra markup, and the canvas stays clean outside comment mode.
- SEO: every public route builds its head with `seoHead(pageSeo(...))` from `lib/seo.ts` (canonical on `SITE_URL` = https://mcotesjames.com, OG/Twitter, robots, JSON-LD); never hand-write meta tags in a route. Automatic values: the site name (homepage) or hero title as the title, the hero intro as the description. Page overrides live in the page row's `seo`, site-wide values in `settings.seo`; empty = automatic. Edited in `components/admin/SeoPanel.tsx` on the page Settings screen (`routes/admin.page-settings.$key.tsx`), which saves live and into any draft. Settings is the only writer of a page's `seo`; editor Publish keeps its live value (`useSiteDraft.publish({ keep })`). `/sitemap.xml` is a server route. Why: every page, however it's made, gets complete tags, and editors only change what they want to.
- Created pages (`lib/pages.ts`, `components/admin/usePages.ts`, `routes/$slug.tsx`): the site_content row `pages` lists `{ key: "page_<letters>", title, slug, published }`; each page has its own row with `intro`, `sections`, `section_data`, `seo`. `/$slug` serves only published ones (and unpublished in the Studio canvas). `PageKey` = `home` + `page_${string}`; keys are letters only so they fit CMS field addresses. The row also holds `names` (a renamed homepage). Pages are managed from `/admin/pages` (Edit = editor, Settings, Duplicate, Delete); any page can be duplicated (`duplicateDoc`); the homepage keeps its address and can't be deleted. Deleting removes the list entry and keeps the row. Why: standard pages are made in the CMS, not by changing code.
- Created pages have a template (`lib/templates.ts`), stored as `template` in the page row (missing = Standard; the homepage is always Standard). The platform ships Standard only; a template sets the starting and required sections, which section types the + menu offers and whether the hero shows. Switching template is a draft edit in the page editor that clears the page's sections (after a warning) and keeps its hero, name, address and SEO; Discard undoes it until Publish. Add new layouts as templates, not new routes. Why: page layouts stay distinct without a second renderer or editor.
- Content routes that open in the Studio canvas use `ssr: canvasSsr` (`lib/studio-mode.ts`): data-only for `?studio=1`, full SSR for visitors. StudioBridge re-applies the latest drafts after any non-manual refetch of site content, and only reports in-place text that was actually typed. Why: drafts arriving mid-hydration caused mismatches, background refetches overwrote drafts on the canvas, and blur events undid panel edits.

- Platform and site (spec sections 8, 9 and 12): everything that varies per site lives in `src/site/` — `site.config.ts` (`defineSite()`, contract and validation in `lib/site-config.ts`), `sections/` (designed sections, rendered with `{ values, cms }`), `routes/` (mounted beside `src/routes` by the virtual routes in `vite.config.ts`; list each top-level address in config `routes`) and `theme.css` (token overrides and the public `.site-*` styles; platform tokens sit in `@layer base` so a plain `:root` rule wins). Platform code reads the site only through `@/lib/site`, never `@/site/…` (ESLint enforces it); never hard-code a site value (name, address, wordmark, media sizes, menu limits or defaults) in platform code. Section types and template keys are strings: look them up with `sectionDef` / `templateDef`, which fall back for ones a site has dropped. CI (`.github/workflows/ci.yml`) runs the type check, lint, tests and build on every push; it never deploys. Why: a platform update must merge into every site without touching what the site built, and content saved under a removed section or template must keep working.
- Compatibility contract (spec section 12): `defineSite()`, the `.site-*` class names, the design tokens and content field names are what every site builds on. Never rename or remove one in a platform change: add the new one beside it, deprecate the old one, and remove it only in a major version with upgrade notes. Migrations only add (tables, columns, copied data); renames and removals come in a later release. Why: a site's theme and content depend on them, CSS breaks silently, and the old Worker briefly runs against the new schema during a deploy.
