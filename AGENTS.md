> [!IMPORTANT]
> This is the MCJames Visual CMS platform repo. It began as a copy of an earlier client build and is
> fully cut off from it: no `.env`, no Supabase project, no Lovable project, no deploy target. Never
> reconnect it to that build's repo, database, Lovable project or Worker, and never name that client
> in code, content or docs. Why: nothing done here may affect the original client's live site.
>
> Never rewrite pushed history (force pushing, or rebasing/amending/squashing pushed commits).

- `cms-platform-spec.md` is the single source of truth for the CMS platform. After any change to the CMS or Studio, update the affected sections and add a dated entry to its change log (section 17); add reusable learnings to section 16. Why: the platform is reused for every site, so the spec must always match what's built.
- Until the D1 swap (spec Phase 2) the site has no database: there is no `.env`, so it builds and its tests run, but it loads no content. Don't add Supabase keys to make it run. Why: the only Supabase project these files ever pointed at is the original client's live database.

- Site content (pillars, stack cards, bio hotspots, partners, insights posts, investments) lives in Cloud tables and is edited at /admin; never hardcode it in components. Why: the client edits content without code changes.
- Admin access = `admin` row in user_roles; the first account to sign up gets it via a database trigger, every later account waits until an admin approves it in Settings → Users (`/admin/users`). Sign-up (AdminGate) collects first and last name into `profiles`; AdminGate asks named-less accounts for a name and provides the signed-in admin via `useAdminUser()`. Why: sign-up stays open without opening the admin, and names identify comment authors.
- Uploaded media goes in the private `media` bucket and is stored as a 10-year signed URL. Why: the workspace blocks public buckets.
- Navigation is a symbol-only brand-left / frosted-glass link-pill-right bar with no scroll-state styling, collapsing into a toggle dropdown below 768px. Why: the always-frosted pill reads over every section without a scroll trigger or measured-width animation.
- Public H1 titles use the letter reveal: wrap their text in `<LetterReveal text=… />` (`components/LetterReveal.tsx`), which renders plain text in the Studio canvas so it stays editable, and a screen-reader copy on the site. Why: one title animation everywhere, without breaking in-place editing.
- Satoshi (300, 400, 500, 700) is the only web font: loaded from Fontshare's CDN in the root head and used by `--font-sans` / `--font-display`, numerals included (tabular figures). Base text weight is `--weight-text` (500) and public H1 weight is `--weight-h1` (400), both in `src/styles.css`; never hard-code `font-weight: 400`. Why: one typeface across the site, with its weight set in one place.
- Section typography uses semantic global classes and tokens; all text H1 sizes use --type-h1. Why: shared responsive scales prevent per-route drift without changing content.
- Homepage Lenis uses the GSAP ticker and forwards scroll events to ScrollTrigger, with native scrolling for reduced motion and cleanup on unmount. Why: keeps document smoothing, anchors, and the horizontal reveal synchronized without affecting administration.
- Until an email sender domain is configured, the footer enquiry opens a validated email draft and never reports it sent. Why: avoids simulating delivery before sending prerequisites are available.
- Route changes use a capture-phase link interceptor driving the native View Transitions API, with the old-page snapshot raised above the new one and a timer (not requestAnimationFrame) wait inside the update callback. Why: the router consumes link clicks before document bubbling, the default snapshot order hides the swipe, and waiting on animation frames deadlocks the transition.
- Name the glass pill and menu toggle themselves for stationary view transitions, never their bar ancestor; name the brand separately. Why: a named ancestor blocks child backdrop blur from sampling the page.
- In `src/styles.css` declare only the unprefixed `backdrop-filter`; never add a hand-written `-webkit-backdrop-filter` alongside it. Why: the CSS build collapses the pair to the prefixed form only, which Chromium ignores, so the frost silently disappears.
- The blended brand mark stays a fixed element outside any layer-forming ancestor: the header itself is static and the bar and the brand are each fixed separately. Why: `mix-blend-mode` only blends against its own group's backdrop, so nesting it inside a fixed + z-index header blends against nothing and the mark never inverts.
- Page text and site settings live in the site_content table (one row per page plus 'settings', live content plus a nullable draft), loaded once in the root loader. Why: one home per page with room for the draft/live flow.
- Content Studio edits go to a nullable `draft` column (posts, site_content); Publish copies draft to the live columns and clears it, public pages read only live columns. Drafts are read only via `lib/admin-drafts.ts`; never select `*` or `draft` on these tables. Why: edits never reach the site until published, and drafts stay admin-only.
- Full-screen editors are `admin_` routes outside the /admin layout and all share StudioShell: the real page in an iframe (`?studio=1`; articles use `/studio/article`, fed the draft by postMessage) where StudioBridge edits `data-cms` text in place and shows hover ↑/↓/+ on `data-cms-section` blocks; the side panel only edits the selected block's fields. Sidebar groups: Feedback, Content (Insights), Records (Investments, Publications), Pages, Library, Settings (Site settings, Users). The editor title is the page switcher (`components/admin/PageSwitcher.tsx`, `lib/page-switcher.ts`): pages, Content → Insights with a › list of articles, orange (unpublished) / purple (unresolved comments) dots, Cmd/Ctrl+K (forwarded from the canvas as `studio-shortcut`), waits for pending saves, and carries `device` / `mode=comment` in the search params. Editors are keyed by what they edit (`PageCanvas key={key}`, `Editor key={id}`). Why: one editor behaviour everywhere, matching the live site, and quick moves between editors without state leaking between them.
- The Content Studio uses its own neutral dark theme: AdminGate wraps every admin screen in `.studio`, and `:root:has(.studio)` in styles.css overrides the colour tokens and the body gradient (brand orange stays as primary). Never restyle admin screens with page-level backgrounds or hardcoded colours. Why: the public site's warm body gradient otherwise shows through the admin, and scoping by `:has` keeps the public site and the editor canvas iframe untouched.
- Pages are a pinned hero plus flexible sections: `lib/page-sections.ts` defines the section library, the once-per-page rule and the original ("legacy") sections, and `components/sections/PageSections.tsx` renders them. A page row stores `sections` (order) and `section_data` (own text of added sections); legacy sections read their original fields and a page with no saved order uses its default layout. Add new section types to the library rather than hardcoding them into a page. Why: every page apart from the hero is editable in the Studio, without migrating existing content.
- Pillars, stack cards and hotspots are edited as drafts: `lib/list-drafts.ts` + `components/admin/useListDrafts.ts` keep each edited list whole in the site_content row `lists` (draft column); Publish upserts it into the list's table (sort = position) and deletes removed rows; the canvas gets the draft lists by postMessage and shows them via the `home` query. Items carry `data-cms-item="<list>:<id>"` for selection. Never write list items straight to their tables from the page editor. Why: list edits follow the same draft/publish rule as everything else, and new items can be previewed on the page before publishing.
- Studio canvas outlines: green (`--studio-section`) for `[data-cms-section]`, light blue (`--studio-inner`) for `[data-cms]`, `[data-cms-image]` and `[data-cms-item]`; dashed on hover, solid when selected. Item outlines sit outside the element unless it carries `data-cms-fill` (fills its section, e.g. pillars, cards), which insets them. Selection flashes are fixed overlays added by StudioBridge. Why: a negative outline offset collapses on small items, and overlays never affect layout.
- In the Studio canvas (`isStudioFrame()`), SmoothScroll (Lenis) is off, and pillars and stacking cards skip their GSAP scroll timelines and use the static layout under `.studio-live` in styles.css. Why: pinned and horizontal scroll sections can't be edited in place.
- Menus are edited on the Studio canvas, not hardcoded: `lib/menus.ts` defines links (which point at a page, insight, page section, URL or email, never a raw path), the footer column limit (3) and defaults that reproduce the original menus; SiteChrome renders them from the site_content row `menus` (draft/live) and hides links whose target has gone. Page sections get an anchor `section-<id>` (`sectionAnchor`) for section links. Edited in the page editor via `components/admin/MenuPanel.tsx` (`data-cms-section="menus:main"`/`"menus:footer"`, links `data-cms-item="menu:<id>"`, columns `"menucol:<id>"`). Why: the client edits navigation visually without code changes, and links survive renames and reordering.
- Empty CMS content is never rendered on the live site: wrap every CMS-fed element, its containers and its section in `useShow()` from `lib/show-if.ts` (`{show(a, b) && …}`; `isFilled` for values that are never edited in place). In the Studio canvas `useShow` always renders, and empty `[data-cms]` text gets an "Empty — hidden on the site" placeholder from styles.css. Empty article blocks are dropped via `blockHasContent` (`lib/modules.ts`). Why: no empty tags, gaps or broken images when the client leaves a field blank, while the field stays fillable in the editor.
- Feedback comments (`comments` table): `lib/comments.ts` (threads, which threads show on a canvas, places), `components/admin/useComments.ts` (data + actions), `CommentThreads.tsx` (new thread, thread view, rows, record comments), `useCanvasComments.tsx` (comment mode in StudioShell editors). Threads are pinned to the canvas's own element addresses (`data-cms`, `data-cms-image`, `data-cms-item`, `data-cms-section`, plus `data-cms-record` = "record:<table>:<id>" / "post:<id>" on record and insight cards in the Studio). StudioBridge only draws pins while comment mode is on, and pauses editing then; a click also stores `comments.position` (path from the anchored element to the clicked element + click point as fractions, see `parsePosition`) so the pin lands on that exact spot, drawn hollow on the nearest visible part when it's inside something closed. Alt/Option-click passes through to the page while commenting. Keep interactive open/closed state in attributes (`data-open`, `aria-hidden`, `aria-expanded`) so pins can tell when content is hidden. Every new canvas element that should take comments needs one of those attributes. Why: comments survive edits and reordering with no extra markup, and the canvas stays clean outside comment mode.
- SEO: every public route builds its head with `seoHead(pageSeo(...))` / `seoHead(insightSeo(...))` from `lib/seo.ts` (canonical on `SITE_URL` = https://mcotesjames.com, OG/Twitter, robots, JSON-LD); never hand-write meta tags in a route. Page SEO overrides live in the page row's `seo`, insight overrides in `posts.seo`, site-wide values in `settings.seo`; empty = automatic. Edited in `components/admin/SeoPanel.tsx` on the Settings screens (`routes/admin.page-settings.$key.tsx`, `routes/admin.insight-settings.$id.tsx`), which save live and into any draft. Settings is the only writer of a page's `seo` and an insight's author / published_at / slug / seo; editor Publish keeps their live values (`useSiteDraft.publish({ keep })`). The editors hold no backend settings. `/sitemap.xml` is a server route. Why: every page, however it's made, gets complete tags, and editors only change what they want to.
- Created pages (`lib/pages.ts`, `components/admin/usePages.ts`, `routes/$slug.tsx`): the site_content row `pages` lists `{ key: "page_<letters>", title, slug, published }`; each page has its own row with `intro` (title, summary), `sections`, `section_data`, `seo`. `/$slug` serves only published ones (and unpublished in the Studio canvas). `PageKey` = built-in keys + `page_${string}`; keys are letters only so they fit CMS field addresses. The row also holds `names` (renamed built-in pages). Pages are managed from `/admin/pages` (Edit = editor, Settings, Duplicate, Delete); any page can be duplicated (`duplicateDoc` turns built-in sections into `section_data`); built-in pages keep a fixed address and can't be deleted. Deleting removes the list entry and keeps the row. Why: standard pages are made in the CMS, not by changing code.
- Created pages have a template (`lib/templates.ts`), stored as `template` in the page row (missing = Standard; built-in pages are always Standard). A template sets the starting and required sections, which section types the + menu offers and whether the page hero shows (its text is kept either way). Switching template is a draft edit in the page editor that clears the page's sections (after a warning) and keeps its hero, name, address and SEO; Discard undoes it until Publish. Add new layouts as templates, not new routes. Why: page layouts stay distinct without a second renderer or editor, and a page never mixes two templates' sections.
- The Interactive section renders an uploaded HTML file from the media bucket in a srcdoc iframe with `allow-scripts allow-same-origin`, normalised by `lib/interactive.ts`; the Studio canvas shows a placeholder instead of the live frame. Why: the client publishes self-built interactives without code changes; same-origin is acceptable because only approved admins can upload, and a live frame would swallow Studio clicks.
- Content routes that open in the Studio canvas use `ssr: canvasSsr` (`lib/studio-mode.ts`): data-only for `?studio=1`, full SSR for visitors. StudioBridge re-applies the latest drafts after any non-manual refetch of site content or lists, and only reports in-place text that was actually typed. Why: drafts arriving mid-hydration caused mismatches, background refetches overwrote drafts on the canvas, and blur events undid panel edits.

- Subdirectories have their own AGENTS.md; read it before changing files there.
